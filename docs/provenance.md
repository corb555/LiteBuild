# LiteBuild Provenance — High-Level Specification

## Overview

It can be difficult to track file provenance in a large build project. Source files may come from many organizations, 
may have cryptic filenames, may be downloaded through interactive websites rather than stable URLs, and may pass 
through many transformation steps before reaching the final output.

LiteBuild can help because it knows how files move through a workflow. Its dependency graph identifies which files are produced 
by workflow steps and which files enter the workflow from outside.

The LiteBuild **Provenance** feature builds on that information to make source-file provenance visible and optionally 
enforce documentation of those sources.

LiteBuild provides four related provenance capabilities:

1. **`PROVENANCE` section** — describes external source files or groups of source files.
2. **Workflow Report** — identifies source files and includes a provenance section.
3. **Provenance JSON** — optionally emits machine-readable provenance for downstream applications and publication tooling.
4. **Provenance Validation** — checks whether source files have matching provenance declarations.

The goal is to provide useful provenance without requiring a separate manually maintained database or catalog
and alert the user when items are missing provenance.

---

## 1. Source Files

For provenance purposes, a **source file** is:

> A file consumed by the resolved workflow that is not produced as the output of another workflow step.
> It can be a data file or a config file.

For example:

```text
LF2024_EVT_CONUS.tif
        ↓
WarpEVT
        ↓
EVT_warp.tif
        ↓
ReclassifyEVT
        ↓
EVT_themed.tif
```

`LF2024_EVT_CONUS.tif` is a source file because it enters the workflow from outside LiteBuild.

`EVT_warp.tif` and `EVT_themed.tif` are not source files because their provenance is already represented by the 
LiteBuild workflow graph.

Source-file status is local to the current resolved workflow. A file may have been generated by another project or pipeline and still be a provenance source for the current workflow when no step in the current workflow produces it.

Source files may include:

- downloaded datasets
- manually created GIS files
- configuration files
- lookup tables
- style files
- other external inputs

## 2. Project Provenance Policy

Provenance checking is controlled at the project level:

```yaml
PROJECT:
  OVERVIEW: >
    Generate naturalistic shaded relief maps from raw Digital Elevation
    Model (DEM) GeoTIFFs and other sources.

  DEFAULT_WORKFLOW_STEP: CreateMBTiles
  PROVENANCE_CHECK: warn
  GENERATE_WORKFLOW_MARKDOWN: true
  GENERATE_PROVENANCE_JSON: true
```

`GENERATE_WORKFLOW_MARKDOWN` controls whether LiteBuild writes the resolved workflow description as Markdown. When enabled, the Markdown report includes a provenance section describing the external source files used by the workflow.

`GENERATE_PROVENANCE_JSON` controls whether LiteBuild writes a machine-readable provenance JSON file for the resolved workflow. Both generation options are independent of `PROVENANCE_CHECK`; provenance output may still be generated when coverage checking is `off`.

`PROVENANCE_CHECK` supports three values:

```text
off
warn
fail
```

### `off`

Provenance coverage checking is disabled.

LiteBuild does not require source files to have matching provenance declarations.

Source-file discovery and provenance display in the workflow report remain enabled. The `PROVENANCE` section, when present, is still subject to normal LiteBuild schema and configuration validation.

### `warn`

LiteBuild checks provenance coverage.

Missing provenance declarations are reported as warnings, but the build remains valid and may continue.

Example:

```text
⚠ Missing provenance:
  input/sources/US_raw_precip.tif
  config/snow_color_ramp.txt
```

This mode is useful while adding provenance to an existing project.

### `fail`

LiteBuild requires complete provenance coverage.

Every source file used by the resolved workflow must match a provenance declaration.

Missing provenance causes validation to fail and the workflow to abort.

Example:

```text
❌ ERROR: Missing provenance for source files:
   input/sources/US_raw_precip.tif
   config/snow_color_ramp.txt
```

## 3. `PROVENANCE` Section

The top-level `PROVENANCE` section documents source inputs.

Example:

```yaml
PROVENANCE:

  landfire_evt:
    INPUT: "{SOURCE_DIRECTORY}/LF2024_EVT_CONUS.tif"
    DESCRIPTION: >
      LANDFIRE Existing Vegetation Type 2024.

  evt_patch:
    INPUT: "{EVT_PATCH_FILE}"
    DESCRIPTION: >
      Manual QGIS corrections to LANDFIRE EVT classifications.

  usgs_13:
    INPUT: "{INPUT_DIRECTORY}/USGS_13*.tif"
    DESCRIPTION: >
      USGS 3DEP 1/3 arc-second elevation data used as the primary
      elevation source.

  usgs_gmted:
    INPUT: "{INPUT_DIRECTORY}/*_gmted_mea075.tif"
    DESCRIPTION: >
      USGS GMTED elevation data used where higher-resolution elevation
      data is unavailable.

  config_color_ramp:
    CONFIG: "{CONFIG_DIR}/*_color_ramp.txt"
    DESCRIPTION: >
      Color-ramp definition files used by the rendering pipeline.

  config_theme:
    CONFIG: "{CONFIG_DIR}/*_theme.qml"
    DESCRIPTION: >
      QGIS category theme definitions used to assign thematic colors.

  config_reclassify:
    CONFIG: "{CONFIG_DIR}/*_reclassify.yml"
    DESCRIPTION: >
      Category reclassification definitions used to convert source
      classifications into LandWeaver thematic classes.
```

The key beneath `PROVENANCE` is a logical identifier only:

```yaml
landfire_evt:
usgs_13:
config_theme:
```

It does not need to correspond to a filename.

It must be unique within the `PROVENANCE` section.

## 4. Provenance Fields

Each provenance item contains exactly one source selector, `INPUT` or `CONFIG`, plus a required `DESCRIPTION`. `ATTRIBUTION` and `CITATION` are optional publication-oriented fields.

```yaml
INPUT: # or CONFIG:
DESCRIPTION:
ATTRIBUTION:  # optional
CITATION:     # optional
```

The fields have intentionally distinct purposes:

- **`DESCRIPTION`** — What is this source and where/how did it come from?
- **`ATTRIBUTION`** — What short credit belongs with the published output?
- **`CITATION`** — What full reference should appear in source documentation?

`INPUT` and `CONFIG` are mutually exclusive.

`INPUT` and `CONFIG` use the same provenance matching rules. The distinction is supplied by the project author to classify a source as data or configuration for documentation and reporting. LiteBuild does not infer the classification from the file path, extension, or workflow behavior.

LiteBuild resolves variables before provenance matching.

Wildcard expressions use standard Unix-style glob syntax, not regular expressions. Supported patterns follow Python-compatible glob semantics such as `*`, `?`, and character ranges such as `[abc]`. Wildcard matching is performed by LiteBuild rather than by the shell.

### `INPUT`

Identifies one or more source _data_ files.

The value may contain:

- LiteBuild variables
- an exact filename
- a wildcard pattern

Examples:

```yaml
INPUT: "{SOURCE_DIRECTORY}/LF2024_EVT_CONUS.tif"
```

```yaml
INPUT: "{INPUT_DIRECTORY}/USGS_13*.tif"
```



### `CONFIG`

Identifies one or more  _config_ files.

The value may contain:

- LiteBuild variables
- an exact filename
- a wildcard pattern

Examples:

```yaml
CONFIG: "{CONFIG_DIR}/*_color_ramp.txt"
```



### `DESCRIPTION`

Human-readable description of the source.

Example:

```yaml
DESCRIPTION: >
  USGS 3DEP 1/3 arc-second elevation data downloaded from the
  USGS National Map and used as the primary elevation source.
```

The description may contain whatever operational provenance information is useful to the project, including:

- data provider
- dataset name
- version
- download location
- acquisition notes
- purpose
- manual creation information
- known limitations

LiteBuild does not attempt to normalize these details into many dedicated fields. `ATTRIBUTION` and `CITATION` are exceptions because they serve distinct publication and documentation purposes.

### `ATTRIBUTION`

Optional short-form credit intended for use with a published output, such as an on-map attribution bar or other compact display.

Example:

```yaml
ATTRIBUTION: "© OpenStreetMap contributors"
```

LiteBuild stores and exports the attribution text but does not prescribe where or how an application displays it.

### `CITATION`

Optional full source reference intended for source documentation, reports, metadata displays, or a detailed sources dialog.

Example:

```yaml
CITATION: >
  U.S. Geological Survey, 2024, 3D Elevation Program (3DEP) 1/3 arc-second
  National Elevation Dataset. https://apps.nationalmap.gov/
```

LiteBuild treats citation text as project-supplied content. It does not validate citation style, URLs, licensing terms, or legal sufficiency.

## 5. Wildcard Provenance

A single provenance declaration may describe many related source files.

For example:

```yaml
usgs_13:
  INPUT: "{INPUT_DIRECTORY}/USGS_13*.tif"
  DESCRIPTION: >
    USGS 3DEP 1/3 arc-second elevation tiles.
```

may cover:

```text
input/USGS_13_n35w107.tif
input/USGS_13_n35w108.tif
input/USGS_13_n36w107.tif
input/USGS_13_n36w108.tif
```

This avoids requiring a provenance record for every tile in a tiled dataset.

The pattern documents the **logical dataset**, not each individual physical file.

## 6. Provenance Matching

After resolving the workflow, LiteBuild determines the set of source files.

For each source file it determines which `PROVENANCE` entry matches the resolved path.

Conceptually:

```text
Resolved workflow
       ↓
Collect every input file
       ↓
Collect every workflow output file
       ↓
Source files =
inputs not produced by workflow
       ↓
Match source files against PROVENANCE
```

An exact `INPUT` or `CONFIG` value matches its corresponding source file.

A wildcard `INPUT` or `CONFIG` value matches any source file satisfying that pattern.

Matching precedence is deterministic:

1. An exact path match takes precedence over any wildcard match.
2. If no exact match exists and exactly one wildcard declaration matches, that declaration is used.
3. If no exact match exists and more than one wildcard declaration matches, the provenance configuration is ambiguous and validation fails.
4. If more than one exact declaration resolves to the same path, the provenance configuration is ambiguous and validation fails.

LiteBuild does not rank wildcard patterns by specificity.

For example:

```yaml
CONFIG: "{CONFIG_DIR}/*_theme.qml"
```

could match:

```text
config/EVT_theme.qml
config/geology_theme.qml
```

## 7. Overlapping Provenance Definitions

An exact path match overrides wildcard matches.

For example:

```yaml
PROVENANCE:

  yaml_config:
    CONFIG: "config/*.yml"
    DESCRIPTION: "LiteBuild YAML configuration files"

  render_config:
    CONFIG: "config/render.yml"
    DESCRIPTION: "LandWeaver render configuration"
```

`config/render.yml` matches both declarations, but the exact `render_config` declaration takes precedence.

Multiple wildcard matches are ambiguous when no exact declaration matches the source file.

For example:

```yaml
PROVENANCE:

  usgs:
    INPUT: "input/USGS_*.tif"
    DESCRIPTION: "USGS raster data"

  dem:
    INPUT: "input/USGS_13*.tif"
    DESCRIPTION: "USGS 1/3 arc-second DEM"
```

For:

```text
input/USGS_13_n35w108.tif
```

both wildcard declarations match and neither is exact. LiteBuild does not attempt to rank wildcard patterns by specificity.

Example:

```text
❌ ERROR: Multiple wildcard provenance entries match source file:
   input/USGS_13_n35w108.tif

Matches:
   usgs
   dem
```

Multiple exact declarations resolving to the same path are also ambiguous and cause validation failure.

Ambiguous provenance is a configuration error for all `PROVENANCE_CHECK` settings, including `off`. It is distinct from missing provenance and is not a provenance coverage failure.

## 8. Workflow Report

When `PROJECT/GENERATE_WORKFLOW_MARKDOWN` is enabled, LiteBuild writes a Markdown description of the resolved workflow. The report includes a **Provenance** section divided into **Data Sources** and **Config Sources**.

Even when provenance coverage checking is disabled, LiteBuild determines source files directly from the resolved workflow and displays any matching provenance declarations. When present, `ATTRIBUTION` and `CITATION` are included with the corresponding provenance entry.

Example:

```markdown
## Provenance

### Data Sources

### LANDFIRE Existing Vegetation Type 2024

`input/sources/LF2024_EVT_CONUS.tif`

### Manual QGIS corrections to LANDFIRE EVT classifications

`input/sources/EVT_patch.gpkg`

### USGS 3DEP 1/3 arc-second elevation data

`input/USGS_13_n35w107.tif`  
`input/USGS_13_n35w108.tif`  
`input/USGS_13_n36w107.tif`

### Config Sources

### Color-ramp definition files used by the rendering pipeline

`config/arid_base_color_ramp.txt`  
`config/humid_base_color_ramp.txt`  
`config/rock_red_color_ramp.txt`
```

Files sharing one wildcard provenance declaration are grouped beneath that provenance description.

Source files without provenance also appear in the report.


```markdown
### Missing Provenance

`input/sources/US_raw_precip.tif`
```

## 9. Provenance JSON

When `PROJECT/GENERATE_PROVENANCE_JSON` is enabled, LiteBuild writes a machine-readable JSON representation of provenance for the resolved workflow. The JSON is intended for downstream applications such as map attribution controls, source dialogs, publication tooling, or other consumers that should not parse the Markdown report.

The JSON is generated from the same resolved provenance data used by validation and the workflow report. It contains only provenance relevant to source files used by the resolved workflow; unused declarations are not emitted as active sources.

Each resolved provenance entry may include:

- logical provenance name
- source type (`INPUT` or `CONFIG`)
- resolved source path or paths
- `DESCRIPTION`
- `ATTRIBUTION`, when supplied
- `CITATION`, when supplied

Example:

```json
{
  "project": "US",
  "segment": "uswest",
  "sources": [
    {
      "name": "osm_source",
      "type": "INPUT",
      "paths": ["input/sources/uswest.osm.pbf"],
      "description": "OpenStreetMap vector data for the US West region, downloaded as an OSM PBF.",
      "attribution": "© OpenStreetMap contributors",
      "citation": "OpenStreetMap contributors (2026). OpenStreetMap data retrieved under the Open Database License (ODbL)."
    }
  ]
}
```

The JSON contains structured provenance data only. LiteBuild does not generate HTML or encode presentation rules such as whether attribution appears on a map canvas, in a popup, or elsewhere.

---

## 10. Source File Ordering

Within the workflow report, provenance entries are grouped by source type: **Data Sources** and **Config Sources**. Files within each provenance entry are sorted by pathname.

Source files without matching provenance are grouped as missing provenance, sorted by pathname, and separated by a blank line when the directory changes.

For example:

```text
config/EVT_theme.qml
config/arid_base_color_ramp.txt
config/landfire_evt_reclassify.yml

input/USGS_13_n35w107.tif
input/USGS_13_n35w108.tif

input/sources/EVT_patch.gpkg
input/sources/LF2024_EVT_CONUS.tif
```

## 11. Provenance Validation

Provenance validation operates on the **resolved workflow**, not  on files found in project directories.

This is important because project directories may contain:

- obsolete files
- experiments
- abandoned datasets
- temporary outputs
- old copies
- files used by unrelated profiles

LiteBuild  only requires provenance for source files actually referenced by the workflow being validated.

For:

```yaml
PROJECT:
  PROVENANCE_CHECK: warn
```

missing provenance produces warnings.

For:

```yaml
PROJECT:
  PROVENANCE_CHECK: fail
```

missing provenance causes validation failure.

For:

```yaml
PROJECT:
  PROVENANCE_CHECK: off
```

no provenance coverage validation occurs.

---

## 12. Profiles and Variable Resolution

Provenance is evaluated after normal LiteBuild variable and profile resolution.

For example:

```yaml
PROVENANCE:

  dem:
    INPUT: "{INPUT_DIRECTORY}/USGS_13*.tif"
    DESCRIPTION: >
      USGS 3DEP 1/3 arc-second DEM.
```

uses the same resolved value of:

```yaml
INPUT_DIRECTORY:
```

as the workflow.

This prevents provenance declarations from having their own separate path-resolution semantics.

Profile-specific workflows therefore naturally produce profile-specific source-file lists.

---

## 13. Manual Sources

Manually created data is a valid provenance root.

For example:

```yaml
PROVENANCE:

  evt_patch:
    INPUT: "{EVT_PATCH_FILE}"
    DESCRIPTION: >
      Manually curated polygons created in QGIS to correct known
      LANDFIRE EVT classification errors.
```

LiteBuild does not require every source to come from an external organization or downloadable dataset.

The purpose of provenance is to explain **where the source came from**, including when the answer is “manually 
created for this project.”

---

## 14. Generated Intermediate Files

Generated intermediate files are not provenance roots and do not require provenance entries.

For example:

```text
LF2024_EVT_CONUS.tif
        ↓
EVT_warp.tif
        ↓
EVT_themed.tif
        ↓
EVT_patched.tif
```

Only:

```text
LF2024_EVT_CONUS.tif
```

requires source provenance.

The provenance of:

```text
EVT_warp.tif
EVT_themed.tif
EVT_patched.tif
```

is already represented by the LiteBuild workflow.

This is a core design principle:

> **Explicit provenance describes workflow roots. LiteBuild itself describes the transformation lineage.**

## 15. Phase 1 Scope

Phase 1 includes:

- identifying source files from the resolved workflow
- optionally generating the resolved workflow Markdown report with a provenance section
- optionally generating machine-readable provenance JSON
- defining a top-level `PROVENANCE` section
- resolving provenance `INPUT` and `CONFIG` expressions using normal LiteBuild variables
- supporting exact filenames and standard Unix-style wildcard patterns
- applying exact-match precedence over wildcard matches
- rejecting ambiguous multiple-wildcard and multiple-exact matches
- classifying provenance entries as `INPUT` or `CONFIG` for reporting
- supporting required `DESCRIPTION` and optional `ATTRIBUTION` and `CITATION` fields
- grouping source files by provenance description
- detecting missing provenance
- detecting overlapping provenance definitions
- supporting `PROJECT/PROVENANCE_CHECK` values:
  - `off`
  - `warn`
  - `fail`
- supporting `PROJECT/GENERATE_WORKFLOW_MARKDOWN`
- supporting `PROJECT/GENERATE_PROVENANCE_JSON`
- workflow reporting, JSON generation, and provenance checking will share helper functions

Phase 1 does **not** require:

- a provenance database
- embedded metadata in output files
- checksums
- download automation
- URL verification
- license validation
- automatic discovery of data providers
- provenance records for workflow-generated files
- provenance records for unused files merely present in project directories

Those capabilities can be considered later if there is a demonstrated need.

---

## Design Principle

The provenance feature remains lightweight:

> **LiteBuild already knows how derived files were created. Provenance only needs to document the external 
> roots of that graph.**

That provides a  powerful provenance tree without creating another metadata system.
